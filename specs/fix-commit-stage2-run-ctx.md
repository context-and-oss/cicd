# Intent: fix the commit composite's stale Stage2.Run call site

## Why

`main` has been red on `Composite smoke test (commit)` for several runs because
`src/composites/commit/main.go` no longer compiles. The unify-commit change left
the source-gate call written for an older `Stage2.Run` shape: it assigned a
single return value and passed no context. At Dagger 0.20.8 a module function
returning a list of objects (`[]*dagger.File`) generates a client binding that
takes a `ctx` and returns `([]dagger.File, error)`, so the old call site was a
compile error. Every commit-stage consumer is blocked until this builds, so the
fix is to realign the call site with the generated signature.

## What changed

Only `src/composites/commit/main.go`, at the single `dag.Stage2().Run(...)` call:

- Thread `ctx` as the first argument and capture the returned `error`, returning
  early on failure like every other fallible step in the function.
- The generated client returns `[]dagger.File` (a value slice), but the artifact
  tail and `finishAudit` operate on `[]*dagger.File`. Convert the value slice to
  a pointer slice once, immediately after the call, so the rest of the function
  is unchanged.

No dependency, SDK, or behaviour changes — `go.mod`/`go.sum` are regenerated by
Dagger at build time as before.

## Decisions

We converted the source-gate slice to `[]*dagger.File` at the call site rather
than reworking `finishAudit` and the artifact-tail construction to value slices,
because the single-object scan calls (`Sbom`, `ScanImage`, `ScanArchive`) return
`*dagger.File` and the aggregation layer (`Evidence().Wrap`) already speaks
`[]*dagger.File`. Converting the one value slice is the smallest change that
keeps a single evidence element type through the whole function.

Verified locally with the exact failing check: `dagger call run --artifact
container` against `testdata/go-app` now compiles, runs, and produces
`combined-evidence.json` with `passed=true`.

## Follow-on: two commit-smoke assertions that surfaced once it compiled

With the composite finally running, `Composite smoke test (commit)` exposed two
source-gate assertions that had never actually run green (hidden behind the
compile error, and the assertions were tightened in a recent `commit-shapes.sh`
change). Both were test/observability gaps, not module logic bugs, and neither
is papered over — every check genuinely runs.

- **SAST (semgrep).** The smoke ran the composite with the default
  `--config auto`, which needs Semgrep-registry auth the sealed scan container
  lacks, so semgrep failed and its named SARIF run vanished. And even when
  semgrep runs, its driver name is `Semgrep OSS`, not `semgrep`, which the
  assertion matched exactly. Fix, both in `scripts/smoke/commit-shapes.sh`: pass
  an explicit ruleset (`p/security-audit,p/secrets`, the realistic path all
  templates use) so semgrep actually scans, and match the driver name as a
  case-insensitive substring. Semgrep now produces real SAST evidence.
- **intent (intent-gate).** A passing intent gate emits no finding, and the
  merged envelope keeps no per-module provenance, so a clean fixture (go-app has
  a valid capsule) left no trace to assert on. Rather than corrupt the fixture,
  the intent module now emits a clean-pass warning ("intent-gate: N artifact(s)
  checked, no violations") — mirroring the "no risk files" warning risk already
  emits — and the smoke accepts either a finding or that warning as proof the
  gate ran.

## Decision: fix the assertions honestly, not cosmetically

We rejected the cheap alternative of emitting a named-but-empty semgrep run to
satisfy the assertion, because that is a green check with no SAST actually
running — the exact false-pass this repo warns against (`security/CLAUDE.md`).
Making semgrep run for real with an explicit ruleset gives genuine coverage.

All three shapes (`container`/`none`/`archive`) pass the full smoke locally.
